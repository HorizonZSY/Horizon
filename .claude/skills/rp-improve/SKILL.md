# /rp-improve — 优化与补全已有 Proposal

先读 `workflow/rules.md` 并全程遵守。标准结构见 `workflow/templates/research-proposal.md`，评分维度见 `workflow/templates/review-rubric.md`。

原则：**先补断链，再补缺节，最后改文字**。论证链上游断了，下游文字改得再好也要重写。

## 模式

| 调用 | 作用 |
|---|---|
| `/rp-improve <文件>` | 完整流程：诊断 → 计划 → 填充 → 优化 |
| `--section <章节>` | 只处理一个章节（适合一步一步推进） |
| `--interview` | 问答式填充：逐节提问，用你的回答成文 |
| `--review <03-review-vN.md>` | 按审稿修改计划执行 MUST，再执行 SHOULD |
| `--corpus <语料>` | 把语料文件作为填充素材来源 |

## Step 0 — 读入与建档

1. 读入 proposal。`.md`/`.pdf` 直接读；`.docx` 用 `pandoc in.docx -t gfm -o in.md` 转换（macOS 没装 pandoc 时，用系统自带的 `textutil -convert txt in.docx`，会丢格式）
2. 如果文件不在 `applications/` 下：新建 `applications/<slug>/`，原稿另存为 `02-proposal-v0-original.md`，**原稿不改**
3. 同时读取已有的 `refs.md`、`01-scope.md`、语料、最近一次 review（如有）和个人档案
4. 官方要求（字数、必备章节）：notes 里没有记录就抓取官网，抓不到就问用户。没有要求时，按模板结构诊断，并在 notes 顶部标注"未对照官方要求"

## Step 1 — 诊断

### 1a. 论证链检查

逐环检查 proposal 是否**明确写出**以下六环，每环引用原文；写不出原文引用的，视为缺失：

```
研究问题 → 文献缺口 → 假设 → 识别策略 → 数据 → 预期贡献
```

| 环节 | 原文引用 | 状态 | 与下一环是否衔接 |
|---|---|---|---|

- 状态分三档：明确 / 含糊 / 缺失
- 衔接检查的例子：假设是否回答了研究问题？识别策略能否检验假设？数据能否支撑识别策略？贡献是否对应文献缺口？
- 指出**最先断开的一环**，这是第一优先级

### 1b. 章节诊断

对照模板逐节打状态：

- **可用**：要素齐全，只需要改文字
- **薄弱**：有内容，但缺关键要素（例如识别策略没写核心假设，贡献没和已有研究比较）
- **缺失**：没有，或只有标题

同时记录每节的字数和预算（按 `/rp-draft` Step 1 的比例）。

### 1c. 快速评分

按 review-rubric.md 的 8 个维度各给一个分数和一句理由，只用于排优先级。完整审稿请用 `/rp-review`。

## Step 2 — 填充计划（先给用户确认）

| 优先级 | 位置 | 现状 | 需要补什么 | 素材来源 | 谁来写 |
|---|---|---|---|---|---|

- 排序：断链环节 → 缺失章节 → 薄弱章节 → 文字优化
- 素材来源按以下顺序取：用户已有文字（proposal 其他部分、语料、毕业论文）→ 已核实文献 → 需要新检索 → 需要用户提供
- "谁来写"分两类：AI 起草；用户本人写（个人动机、导师匹配的个人理由、数据是否已拿到这类只有用户知道的事实）
- 计划确认后再动手；用户只想改某一节时，直接跳到那一节

## Step 3 — 填充

- 缺失内容优先用用户自己的素材成文；需要新文献时按 `rules.md` 检索并核实，结果写入 `refs.md`
- 只有用户知道的信息不编造。插入 `[USER: <具体问题>]`，问题要具体到能直接回答，例如 `[USER: 省级补贴数据是否已拿到？年份覆盖到哪年？]`
- AI 新写的段落，开头加 `<!-- AI-FILLED -->` 标记（定稿前删除），方便用户识别哪些需要自己过一遍
- 常见的补法：
  - 研究问题不清 → 压成一句"X 如何影响 Y（情境 C）"，子问题不超过 3 个
  - 缺假设 → 每条写预测方向和拒绝条件
  - 缺识别 → 写估计方程、核心识别假设、主要威胁、对应检验（可参考 `/rp-scope` Step 5 的表）
  - 缺数据 → 写数据表（来源、单位、年份、关键变量、获取方式、状态），获取方式要去官网核实
  - 缺风险 → 每条风险配一个备选方案

## Step 4 — 优化

- **最小改动**：标为"可用"的段落只修错误和强度膨胀修辞，不重写，保持用户原来的论证顺序
- 贡献改写成："Relative to [strand], this project [does what], which allows [testable increment]."
- 删掉开场白、没有数字的形容词、"not … but …"式论证（见 `/rp-draft` Step 2 的清单）
- 超字数时，先删重复表述，再压缩文献综述，最后才动研究设计
- 检查摘要、引言、方法三处的研究问题表述是否一致

## `--interview` 问答式填充

一次只处理一节，按诊断出的优先级排序：

1. 说明这一节缺什么（1–2 句）
2. 提不超过 3 个问题，每个问题都要能用一两句话回答
3. 用户回答后，把答案写成段落，尽量保留用户的原话和原来的想法；展示这一节修改前后的对照
4. 用户确认后进入下一节；用户说"停"就保存当前进度

## `--review` 执行审稿意见

读入 `03-review-vN.md` 的修改计划：先做 MUST，再做 SHOULD；CONSIDER 只在不增加字数时做；DISAGREE 不执行。每一条都要在 notes 里写明处理结果：已解决 / 部分解决 / 未解决，以及改在了哪里。

## Step 5 — 输出

- `applications/<slug>/02-proposal-v<N+1>.md`，旧版本保留
- `applications/<slug>/02-notes-v<N+1>.md`，包含：
  1. 诊断表（论证链、章节状态、快速评分）
  2. 填充计划及每一项的执行情况
  3. 修改日志：按章节列出改了什么、为什么改
  4. 最需要用户回答的问题（不超过 5 个，对应正文里的 `[USER: …]`）
  5. 按 `rules.md` 第 6 节格式写的修改汇报
- 在对话中只输出：最先断开的环节有没有修好、剩下的 `[USER]` 问题、建议的下一步（通常是 `/rp-review <slug>`）
